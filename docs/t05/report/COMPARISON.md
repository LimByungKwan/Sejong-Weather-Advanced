# T05 · 대화가 끊겨도 이어지는 프로젝트

## 같은 기능, 같은 검사

기존 세종 날씨 저장소를 Import하고, 조회 후 30분이 지나면 ‘최신값’이 ‘오래된 값’으로 자동 전환되는 기능 하나를 개선했다. 조회 실패 시 마지막 정상 기온을 유지하고, 성공하면 상태를 복구한다.

작업 전 고정한 검사 10개와 입력·기대값은 [고정 검사](fixed-tests.json), 공통 최초 요청과 상한은 [계획](PLAN.md)에 보관했다. 공통 상한은 세션별 30분, 사용자 요청 10회다. 도구 내부 실행 횟수가 아닌 사용자가 보낸 요청을 센다.

## 인수인계와 순서

날짜는 2026-10-17, 시간대는 Asia/Seoul이다.

1. 세션 1: 최초 요청 수신 17:46:28. 고정 계약 커밋 후 구현 시작 17:48:14.360507. 산출물 저장 시점 17:50:19.214320. 대화 기록에서 확인한 최종 ZIP 전달 답변 시각은 17:51:13이다. 최초 요청 수신부터 전달 답변까지 4분 45초다. 산출물 체크포인트와 답변 전달 시각을 구분했다.
2. 인계: 저장소와 원본 HANDOFF.md를 전달했다. 세션 1은 시간 예약과 화면 연결을 남긴 상태에서 종료했다.
3. 세션 2: 19:21 시작. 19:22 응답에서는 네트워크 제약으로 저장소를 받지 못했다. 19:24 저장소 bundle을 제공해 재개했다.
4. 세션 2: 19:26 최종 응답과 결과 bundle 수신. 새로운 폴더에서 시작 HEAD와 인계 문서 해시를 확인하고, 9/10을 재현한 뒤 기능을 완성했다.

대화 전문은 전달하거나 보고서에 싣지 않는다. 전달 대상은 저장소와 인계 문서였다. HANDOFF.md SHA-256은 `01ffbf120a049e82e5ad770a0e4b801ee3776a34b8e8be6248c1f35774f7370d`로 전달·수신 확인값이 같다. A의 원래 수신 확인 필드는 null 상태로 보존했고, B의 확인 기록은 HANDOFF-B.md에 별도로 남겼다.

7항목 원본 인계는 저장소 루트의 HANDOFF.md, 수신 및 완료 기록은 HANDOFF-B.md에 있다. B는 인수 당시 누락 없음으로 기록했지만, 이후 사용자 환경에서 빌드 설정과 로컬 DB 초기화 안내 누락을 발견했다. 원본 문서를 덮어쓰지 않고 [후속 검증 및 보완](POST-B-VERIFICATION.md)에 수정 전후와 실행 방법을 기록했다.

## 종료 후 검증

사용자 Windows 환경에서 고정 검사 10/10, 고정 파일 원본 일치, 캐시 없는 TypeScript 검사 종료 코드 0, 최종 빌드 완료를 확인했다. 브라우저에서는 정상 조회, 오프라인 실패 시 기온 유지, 성공 시 복구, 30분 경과 후 자동 상태 전환을 확인했다. 세부 결과는 후속 검증 문서에 기록했다. 이 실행들은 세션 2 종료 후 검증이며 세션 2의 사용량·실행 회차에 합산하지 않는다. 탭 복귀 경계 검증과 공개 URL 시크릿 확인은 아직 미완료다.

## 본인 판단

- AI에게 맡긴 일: GPT에 검사 10개와 인수인계 문서 작성을 맡기고, 클로드에는 남은 자동 전환 기능 구현을 맡겼다.
- 직접 판단한 일: 기존 세종 날씨 프로젝트를 바탕으로 개선하기로 정했고, 오프라인 실패·재시도 복구·30분 뒤 자동 전환은 직접 실행해서 확인했다.
- AI 제안을 따르지 않은 일: GPT가 새로 만드는 방향을 제안했지만, 이전 작업을 이어가는 과제 취지에 맞게 기존 세종 날씨 저장소를 Import해서 진행했다.

도구 선택 기준: 다음 작업도 익숙한 GPT로 먼저 시작하고, 고정 검사 통과 수·요청 수·인수인계 재현 결과를 보고 다른 도구로 이어갈지 판단하겠다.

측정표의 판정 구간에는 서비스와 모델 이름을 표시하지 않았다. 정확한 모델 표시명은 별도 근거 확인이 필요하며 추측하지 않는다.
